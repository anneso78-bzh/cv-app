# Journal de session — Application CV Angular

Ce document récapitule les fonctionnalités réalisées et les décisions prises pendant la session de développement et de préparation du déploiement.

## Objectif du projet

Faire évoluer un CV initial en une application web Angular fonctionnelle, synthétique et adaptée à une présentation professionnelle. L'application présente des expériences en développement back-end, composition documentaire (CCM) et protection des données (DPO), avec un backend Node.js pour la génération d'un CV PDF.

## Application et présentation du CV

- Mise en place d'une application Angular avec un CV compact sur une page, organisé en deux colonnes et adapté aux écrans mobiles.
- Ajout de vues/filtres de présentation CCM, DPO et complète, ainsi que d'un onglet de consultation et de copie de la source JSON.
- Réorganisation des expériences selon les vues CCM et DPO.
- Présentation distincte des environnements CCM visés, Quadient Inspire et OpenText Exstream, comme objectifs d'apprentissage et non comme expériences ou compétences déjà acquises.
- Retrait du simulateur CCM interactif à la demande de l'utilisateur.
- Ajout et ajustement des éléments visuels : icônes SVG, icône de langue, couleurs différenciant les expertises CCM et DPO, et favicon illustré.
- Mise à jour des compétences mises en évidence, notamment JSON, PDF, Markdown, SQL, DPA, rigueur et esprit d'analyse.
- Ajustement du texte de mobilité dans les données du CV pour préciser la proximité des gares.
- Retrait du téléphone et de l'adresse e-mail en clair du JSON public. L'adresse e-mail est reconstruite côté client ; cela réduit l'exposition au moissonnage automatisé mais ne constitue pas un contrôle d'accès.

Les données structurées du CV sont conservées dans `src/assets/data/cv-data.json` et décrites par un modèle TypeScript. Les textes sont affichés par les mécanismes de binding Angular, sans insertion directe de HTML fourni par les données.

## Génération et téléchargement du PDF

- Ajout d'un serveur Express en TypeScript.
- Création de la route `GET /api/cv.pdf`, qui génère un PDF A4 à fond blanc à partir du JSON canonique du CV.
- Ajout d'un lien de téléchargement dans l'application et d'un proxy Angular pour le développement local.
- Le PDF a été vérifié : réponse HTTP 200, téléchargement avec nom de fichier, format A4 et contenu sur une page.
- Les erreurs de génération sont journalisées côté serveur et renvoyées avec un statut HTTP 500.

## Configuration et commandes

Scripts npm utiles :

| Commande | Fonction |
| --- | --- |
| `npm start` | Lance le serveur de développement et Angular. |
| `npm run build` | Compile l'application Angular puis le serveur TypeScript. |
| `npm run start:server` | Lance le serveur Node compilé depuis `dist/server/server.js`. |

En local, Angular est servi sur le port 4300 et le backend de développement sur le port 3000. Le proxy de développement redirige les appels `/api` vers le backend.

La compilation complète a été exécutée avec succès, y compris après l'adaptation à Alwaysdata :

```bash
npm run build
```

Le résultat Angular est généré sous `dist/cv-ccm-portfolio/browser`. Le serveur compilé se trouve sous `dist/server/`.

## Déploiement sur Alwaysdata

Le site Node.js Alwaysdata doit écouter sur l'adresse indiquée par `IP` et le port indiqué par `PORT`. Le serveur lit ces variables d'environnement, avec `::` et `3000` comme valeurs par défaut pour un usage local. Il ne faut pas coder en dur le port `8100` fourni par Alwaysdata.

La commande à saisir dans le champ **Commande du programme** est :

```bash
node ~/cv-app/dist/server/server.js
```

Le répertoire du site doit correspondre à `~/cv-app`. Le serveur sert aussi les fichiers Angular compilés si le dossier de production est présent.

Procédure de déploiement utilisée :

1. Installer toutes les dépendances sur l'ordinateur local (`npm ci`).
2. Construire le frontend et le backend avec `npm run build`.
3. Envoyer le dossier de production sur Alwaysdata :

   ```bash
   scp -r dist ashamon@ashamon.alwaysdata.com:~/cv-app/
   ```

4. Démarrer ou redémarrer le site Node.js avec la commande configurée ci-dessus.

`dist/` est ignoré par Git : il n'est pas récupéré par un `git pull` et doit donc être transféré après chaque nouvelle compilation destinée à la production.

## Dépannage rencontré

### `sh: 1: ng: not found`

Cette erreur signifie que la CLI Angular (`ng`) n'est pas installée dans les dépendances disponibles. Elle peut survenir après une installation limitée aux dépendances de production, par exemple `npm ci --omit=dev`, puisque `@angular/cli` est une dépendance de développement.

Le build doit être exécuté dans un environnement local avec les dépendances de développement installées. Il n'est pas nécessaire d'installer Angular CLI globalement sur Alwaysdata.

### Avertissements npm de dépréciation

Des avertissements concernant `jpeg-exif` et `crypto-js` ont été signalés pendant l'installation. Ces paquets sont des dépendances transitives de PDFKit et ne sont pas importés directement par l'application. Les avertissements ne signifient pas à eux seuls que l'installation a échoué ; le build a ensuite réussi.

### `npm ci` interrompu sur Alwaysdata

Une installation complète des dépendances a été interrompue sur l'hébergement, vraisemblablement en raison des ressources disponibles. La stratégie retenue est de construire localement et de transférer `dist/` sur Alwaysdata. Si les dépendances de production du serveur doivent être installées à distance, la commande envisagée était :

```bash
npm ci --omit=dev --no-audit --no-fund
```

### Syntaxe SCP

Le chemin distant doit être précédé de `:` après le nom d'hôte. La commande correcte est `scp -r dist ashamon@ashamon.alwaysdata.com:~/cv-app/`.

## Documentation et sécurité

Le guide d'architecture existant est `Architecture_Angular_CV_CCM_Securise.md`. Il décrit notamment le lancement, la structure, les fonctionnalités, les limites de confidentialité et les recommandations de sécurité.

Les assets Angular sont publics : aucune donnée secrète ne doit être placée dans le JSON ou dans le code client. L'obfuscation de l'e-mail n'est pas une protection d'accès. Une clé de déchiffrement remise au visiteur dans l'URL ne rendrait pas les données confidentielles vis-à-vis de ce visiteur.
